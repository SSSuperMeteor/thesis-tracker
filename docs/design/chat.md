# 本机网页的公司对话（chat）

本文记录第三轮新增的"按公司对话"：范围、存储、工具、校验规则 C01–C03、
限额、用量与费用、提议流程与界面。**每节标注 已定 / 待定**。

术语补充（承接 [webapp.md](webapp.md) 的术语表）：

- **对话（conversation）**：一家公司的一次独立会话。一家公司可以有任意多个，
  彼此完全隔离。
- **回合（turn）**：一条用户消息到一条可发布回答之间的全部工作，含若干次模型请求。
- **占位符（placeholder）**：`{fact:<事实编号>}` 与 `{card:<卡编号>:<字段>}`。
  模型只写占位符，数字由 Python 渲染。
- **证据集（evidence set）**：本对话工具返回过的事实、`compare_facts` 算出的
  派生事实，以及本对话读过的建议卡里的字段。按对话存储，永不跨对话共享。
- **提议（proposal）**：模型请求生成新建议卡的记录；只有用户确认才真正建任务。

---

## 1. 范围与边界（已定）

对话只讨论**一家公司**（外加作为基准的 SPY）。用户可以：

- 问这家公司的本地数据：价格、指标、财务指标；
- 问已有的建议卡：动作、倾向、周期、价位、创建时间；
- 问"现在能不能买"，得到的是**引用现有卡**的回答，或一个"生成新卡"的提议。

对话**不会**：

- 给出新的买点、止损或目标价；
- 在正文里直接写动作词；
- 读取财报原文、新闻或任何文本检索结果；
- 自己启动一次分析。

依据：用户对本轮的边界要求，以及 Stage 2 的 `qa.sec_qa.answer_sec_question`
属于文本检索、不在本轮范围内。

## 2. 存储（已定）

`data/webapp/chat.db`（与 `jobs.db` 同目录，`data/webapp/` 已在 `.gitignore` 中）。
五张表：

| 表 | 内容 | 可变性 |
|---|---|---|
| `conversations` | 编号、公司、标题、钉住的卡、创建时间、归档标记、最近活动 | 可更新（改名、归档） |
| `messages` | 角色、正文、模板正文、片段、被拒草稿与违规项、尝试次数、提示词版本、`reply_to` | **只追加** |
| `chat_tool_calls` | 工具名、参数、字节数、原样 envelope | 只追加 |
| `chat_model_calls` | 每轮请求/返回模型名、fingerprint、输入/输出/缓存命中 token | 只追加 |
| `proposals` | 周期、理由、状态（待确认/已确认/已忽略）、任务编号、卡编号 | 状态受保护地转移 |
| `conversation_facts` | 本对话的证据集，按 `(对话, 编号)` 唯一 | 同编号同值可重复写入 |

两条性质由 SQLite 触发器保证，而不是靠约定：`messages` 的 `UPDATE` 与 `DELETE`
都被 `RAISE(ABORT)` 拒绝（被拒的回答带着违规项存档，而不是被覆盖或删除）；
对话只能归档，没有删除路径。`proposals` 的确认是一条
`UPDATE ... WHERE status='pending'`，所以双击不会排入两次付费分析。

同一编号在同一个对话里出现不同数值时**报告冲突**，不覆盖：早先的回答可能已经
引用了那个值。

## 3. 标题与列表（已定）

标题是**第一条用户消息的前 24 个字符**，读取时计算，不调用模型。助手或系统消息
不会设置标题。公司页列出该公司未归档的对话，含条数、累计 token 与费用、
最近活动、是否有待确认的提议。

## 4. 工具（已定）

模型只能看见七个工具，英文描述，schema 与分发层的一致性由测试保证
（每个 schema 声明过的参数，`accepted_arguments` 都必须接受）：

| 工具 | 说明 |
|---|---|
| `get_price_history` | 本地日线价格；省略 `resolution` 取最新页，给 `resolution` + `fields` 取分档历史 |
| `get_indicators` | 本地复权指标（均线、RSI、MACD 柱、成交量比） |
| `get_fundamental_metrics` | 八项 point-in-time 财务指标，算不出的带原因 |
| `list_cards` | 本公司的建议卡列表（判断，不是事实） |
| `get_card` | 一张卡：判断字段、它自己的事实表、价位伪事实 |
| `compare_facts` | 两个事实的算术，返回可引用的派生事实（界面标注"计算结果"） |
| `request_new_card` | **只**写一条待确认提议；`reason` 里不能有价位或任何数字 |

两条硬约束：

- **日期由程序注入。** 模型传 `as_of` 会被直接丢弃，不协商。§2 的
  [agent-loop.md](agent-loop.md) 里分析循环是"拒绝并返回结构化错误"；对话里
  改为忽略，因为用户的问题不涉及日期选择，让它成为一次可修正的失败没有意义。
- **公司受限于本对话。** 只有本对话的公司与 SPY 可以查询，其它代码返回
  `ticker_not_in_conversation`，消息里给出可用代码。SPY 是基准，不是第二个标的。

### 4.1 卡字段是伪事实（已定）

卡的动作、倾向、周期、买点上下沿、止损、目标、创建时间都以
`card|<卡编号>|<字段>` 为编号进入证据集，`annotation` 为 `AI 判断`，
来源显示为"建议卡（AI 判断）"。这样"收盘价离止损多远"就是一次确定性的减法，
而不是模型心算；同时读者一眼能看出那是判断而不是公司事实。

### 4.2 compare_facts（已定）

`op` 共五个，每个都在派生事实里记下公式与来源编号：

| op | 公式 | 结果单位 |
|---|---|---|
| `difference` | `a - b` | 与被减数相同 |
| `addition` | `a + b` | 与被加数相同（两者单位必须相同） |
| `ratio` | `a / b` | `ratio`（无量纲，4 位小数） |
| `pct_change` | `(a - b) / b * 100` | `percent` |
| `product` | `a * scale` | 与被乘数相同；对 `ratio` 乘 100 时是 `percent`；`scale` 的来源见下 |

- 单位必须相同，`ratio` 除外（它本来就无量纲）；`product` 只接受一个显式
  `scale`，因为"区间的一半"必须能被表达，否则模型只能自己编数字。
- **scale 白名单（已定，第四轮）。** 若 scale 可由模型任意填写，"收盘价 × 1.3"就会作为派生事实出现，
  等于绕过"聊天不给目标价"。所以 scale 只能来自两处，其余一律返回结构化错误 `unsupported_scale`，
  且不向证据集添加任何东西：
  1. **命名常量**：`midpoint` = 0.5（区间的一半，用来算买点中点）；`percent` = 100（只能乘在无量纲的
     `ratio` 上，使之读作百分数，用在价格上是 `scale_not_applicable`）；
  2. **用户本条消息里写过的数字**（只算这一条消息，只算精确相等；更早的消息里的不算）。
  上一轮的 `(0.5, 1, 2)` 里 1 没有作用、2 能把价格翻倍，两者都已删除。派生事实的来源里记录
  `scale_source`（`named:midpoint` / `named:percent` / `user_message`）。`scale` 用在 `product` 以外的操作上是
  `scale_not_used`（以前被静默忽略），错误里告诉模型用 `pct_change` 或 `product` + 100。
- **界面标注（已定）**：派生事实在证据面板里的行带"计算结果"标签，悬停显示公式与来源编号
  （`a - b，a = <编号>，b = <编号>`）；回答正文里引用它的事实标记用实线下划线并有同样的悬停。
- 除数为零返回 `division_by_zero`，不返回无穷大也不猜。
- 结果编号是 `sha256(a|b|op)` 的前 24 位，所以同一次比较永远是同一个编号。
- `pct_change` 的值是**百分数**（3.88），不是比例（0.0388）：`evidence.display_text`
  对 `percent` 会再乘 100，与分析卡的口径一致（存档的毛利率 0.5 显示为 50.00%）。

**残余风险（已知，未处理）**：`addition` / `difference` 等仍然允许把两个价位类事实相加相减
（例如收盘价加两倍 ATR 要靠 `addition` 自加，现在 `scale=2` 已不可用，但 `addition(atr, atr)` 仍可）。
这类结果同样被标成"计算结果"，系统提示词第 7 条禁止给新价位，C01–C03 不变；是否限制价位类事实的加法
**待定**。

依据：本轮"引用现有卡 + 确定性算术"的要求；`pct_change` 的刻度由
`decision/evidence.py:151` 的 `number *= 100` 反推得到，并由
`scripts/chat_spot_check.py` 在真实 NVDA 卡上核对到卡自己印的 3.88%。

### 4.3 不暴露的东西（已定）

没有文本检索、没有新闻、没有文件读取。测试直接断言工具名集合里不含
`search_filings`、`get_news` 之类的入口。

## 5. 校验规则 C01–C03（已定）

回答是一段**模板**：模型写散文，数字只用占位符。发布前逐条机械校验，
**所有**违规项一起返回。

| 编号 | 规则 |
|---|---|
| C01 | 正文里的数字必须写成占位符。例外只有 ISO 日期、财期（`Q1`–`Q4`、`2026-Q3`）、"3 个季度"这类时间计数，以及**用户本条消息里自己写过的数字**。规则本体是 `core.free_numbers`——与卡片校验器 D02 同一个函数，不会漂移。 |
| C02 | 动作词只能通过 `{card:<卡编号>:action}` 出现。词表是 `core.chat_action_words`（D11 的六个类别）。**不设否定放行**：对话没有理由提到一个自己不发出的指令，规则越简单越可证明。 |
| C03 | 每个 `{fact:...}` 必须在本对话证据集里，每个 `{card:...}` 必须是本对话读过的卡且字段存在。跨对话、跨公司、不存在的编号都拒绝。没有闭合的占位符、嵌套花括号也算 C03——半个事实编号不能当散文给读者看。 |

另有两条**限制类**检查，不属于 C 规则、不改变 C01–C03：`L05`（工具调用次数用完）与 `L06`
（回答是空的）。空文本没有数字、动作词和占位符，所以没有任何 C 规则会反对它——第一次真实运行发布了两条空消息，
现在它和别的违规一样被退回修正。

违规时：把全部违规项（规则编号、位置、中文说明）回给模型修正，**最多 2 次**；
第三次仍失败则该回合失败，只显示违规报告与"这条回答没有通过检查"，
被拒草稿**绝不**出现在回答位置。每一次尝试的原始草稿都存档，接口不回传草稿正文
（只有 `has_draft` 与逐次违规项）。页面上只展示**最后一稿**的违规项：
三稿通常违反同一条规则，重复三遍会淹没重点，而次数仍然写明。

发布后由 Python 渲染成片段数组：`{"type":"text"}`、`{"type":"fact"}`、
`{"type":"card"}` 与系统消息的 `{"type":"card_link"}`。逐段拼接必须与整段文本
逐字节相同，这条由测试断言。注解有两条，都为了不让判断被读成事实：

- 卡字段：`（AI 判断，建议卡 <8 位>，YYYY-MM-DD）`；
- 自己日期不是本回合最新价格日的**事实**：`（截至 YYYY-MM-DD）`。

注释同时作为独立字段随片段下发，页面可以安静地排版，不必从句子里反解。

## 6. 上下文与限额（已定）

发给模型的东西只有三样：系统提示词（含版本号，存进 `messages.prompt_version`，当前是
`chat-v2-2026-10-05`；v2 的变化见第 11 节）、
公司简报（**只有**代码与最新价格日）、以及钉住的卡（如果这个对话是从某张卡开始的）。

历史是**最近 12 条**消息，以**模板形态**发送——上一轮回答的 `{fact:...}` 占位符
原样回传，而不是渲染后的数字。这正是让模型继续写占位符、而不是开始直接打数字的
原因。更早的消息仍然存档、仍然显示，页面标注"较早的消息不再发给模型"。
**不做**模型摘要。

| 限额 | 值 | 作用 |
|---|---|---|
| 每回合工具调用 | 8 | 防止无限查数据 |
| 每回合模型请求 | 10 | 防止无限循环 |
| 每回合修正 | 2 | C01–C03 的第三次失败即结束 |
| 单次请求预估输入 | 200,000 token | 超过就不发请求（与分析循环同一个保守估算：1 字节 ≤ 1 token，再加 2,048 留量） |
| 单回合累计 token | 300,000 | 超过即失败 |

**没有**对话级或公司级累计上限：用户要的是知道一回合花了多少，不是被限额。
余额不足或 API 报错时该回合失败并给出原因，**不重试**；异常只按类型记录，
避免 SDK 错误文本里的请求头进入存档。

## 7. 用量与费用（已定）

四个层级，各自标明范围：本条消息、本对话、该公司全部对话、今天（本机日历日）。
金额只从**存储的逐次调用行**算出，不用运行中的计数器，所以重启不会丢。

价格**不硬编码**：`data/webapp/pricing.json`（本地、不入库）+ 随代码提交的模板
`webapp/chat/pricing.default.json`。文件缺失或字段不全时**只显示 token**，
并写明"未找到价格配置"——半个价格等于一个错的金额，比没有更糟。
缓存命中按缓存价计费，未命中数是输入减去命中数，所以命中不会被收两次、
命中数超过输入也不会抬高金额。

初始值取自官方价格页（2026-10-05 读取）：缓存命中 $0.006、未命中 $0.30、
输出 $1.20 / 百万 token。用的是**高峰价**，因为低峰价是高峰价的一半，
所以高峰价是保守上界；每个金额都带"按高峰价上界估算，实际可能更低"与价格日期。

余额走官方文档的只读接口 `GET https://api.deepseek.com/user/balance`
（返回 `is_available` 与 `balance_infos`），只在服务端请求，API key 从环境变量读、
永不回传给页面；查询失败就如实报告失败，不编造余额。

## 8. 提议与生成（已定）

1. 模型调用 `request_new_card(horizon, reason)`，只写一条 `pending` 提议。`reason` 带自由数字（价位等）
   会被拒绝（同 C01 的规则）：新卡的买点、止损、目标由分析流程自己给出，**不接受用户指定的价位**，
   所以提议里不能暗示"以 300 为参考"（第一次真实运行里就出现过）。
2. 页面显示提议面板：周期、理由、"将调用 DeepSeek 并按量计费，最近 N 次分析平均用了
   X 输入 / Y 输出 token"（来自 `/api/usage`，前端不写死任何数字）、确认生成 / 忽略。
3. 确认走**与分析按钮完全相同**的路径：同一个 `kind=analyze`、同一套参数校验、
   同一个工作线程。对话没有第二条花钱的路。
4. 分析日期取**最新已存价格日**，不是今天——D03 会拒绝晚于价格数据的 `as_of`，
   提供一个注定失败的确认是陷阱。
5. 任务到达终态后对话里**恰好追加一条**系统消息：成功时是卡链接（数据全部来自
   存档，由既有渲染器给出），失败时是失败原因。去重由提议自己的 `card_id` 保证，
   刷新不会重复；运行中的任务不追加任何东西。这条路径**不调用模型**，
   测试用"构造函数就抛异常"的假客户端断言这一点。
6. 已确认的提议再次确认返回冲突，已忽略的永远不能确认，任务失败不留半张卡。

## 9. 接口（已定）

全部沿用令牌 / Host / Origin / POST-only / 64 KiB 上限，CSP 不变。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/companies/conversations?ticker=` | 该公司的对话列表 |
| GET | `/api/conversations/<编号>` | 对话、消息、证据集、用量、启动块 |
| POST | `/api/companies/conversations` | 新建对话（可带 `card_id` 钉卡） |
| POST | `/api/conversations/<编号>/messages` | 发消息，创建一个 `chat_turn` 任务 |
| POST | `/api/conversations/archive` | 归档 |
| POST | `/api/proposals/confirm` | 确认提议（创建分析任务） |
| POST | `/api/proposals/dismiss` | 忽略提议 |
| GET | `/api/balance` | 只读余额 |

**对话的公司永远取自存储的对话记录**，不取请求体：请求里带 `ticker` 不会改变
这个对话讨论谁。发消息不弹确认框，但输入框旁边常驻"每条消息会调用 DeepSeek
并按量计费"。消息长度上限 4000 字符。

**回合状态（已定，第四轮）**：对话视图带 `turn`（`idle` / `queued` / `running` / `failed` / `interrupted`、
`in_flight`、中文标签与原因）。页面只在有回合进行、或已确认提议的分析还没出结果时每 1.5 秒看一次，其余时候
不轮询；回合以"没有任何回答"结束（模型连不上、软件重启）时，页面上有一条错误说明并允许重问，被拒的回答
不算（它本身就是一条消息）。同一对话有回合在进行时再发消息返回 **409**（检查与写入在同一把锁里）——否则
两条消息排队时，第一回合的历史里会含有它自己、第二条的问题则不在任何历史里。

任务槽位：分析仍然"同时只跑一个"；对话**全局最多 2 个**同时进行，且
**同一对话同时只有 1 个**回合。整个判定在一条 `BEGIN IMMEDIATE` 事务里，
两个线程抢最后一个空位时只有一个能赢（测试用 6 个线程抢 5 个回合断言恰好 2 个成功）。

## 10. 界面（已定）

- 公司页新增"对话"段：标题、条数、累计 token 与费用、最近活动、待确认标记，
  右上角"新建对话"。
- 对话页 `#/chat/<编号>` 复用卡片详情的两栏阅读 + 证据布局与证据面板组件。
  证据行由 `webapp.service.fact_rows` 统一生成，所以同一个事实在哪个页面读起来都一样。
- 消息呈现是**结构差异**，不是配色差异：用户消息是浅底块，回答是正文文本；
  没有气泡、没有渐变（布局检查脚本同时断言两者底色不同且都不含渐变）。
- 消息区在限宽的阅读栏里；**输入区固定在栏的底部**（`position: sticky`），回合进行中禁用并写明
  "已排队，等待回答 / 正在回答"。
- 工具调用折叠成"查了 N 次数据"，展开是名称、参数、字节数。
- 被拒回答显示违规报告，**永不**显示草稿。
- 输入区多行，Enter 发送 / Shift+Enter 换行。
- 用量在输入区下方以**小号次要色一行**显示（本对话与今天的 token 与估算费用，后端拼好整句），
  "明细"展开四个层级的表。
- 提议是带边线的卡片；处理过的提议保留成一行安静的状态（已确认 / 已忽略，含任务链接），刷新后仍在。
- 空状态是行动入口：四个可直接点击的问题。
- 卡详情新增"追问这张卡"，新建一个钉住该卡的对话。**不新增顶级导航项**。

## 11. 第一次真实运行（已定的结论）与待定

条件与逐回合结果见 [../qa/webapp-audit.md](../qa/webapp-audit.md) 第 5 节：NVDA 对话 10 回合 + 1 次界面确认的新卡，
共 359,283 token。

**已定**：

- **thinking 模式关闭是可用的**：10 个真实回合（含并行工具调用与多轮工具调用）都在非思考模式下正常完成，
  没有任何 `reasoning_content` 相关错误。
- 真实运行里 C01–C03 **没有被放宽**，也没有发现校验器自身的错误；暴露的是提示词与工具的问题
  （五项，已修，提示词 v1 → v2）：双花括号、空回答、被静默丢弃的 scale、"卡里没有理由"的不实说法、
  提议理由里的价位。**修复后没有用真实模型复验**（回合额度已用完），各有离线测试。

**待定**：
- **非思考模式下的 JSON 输出**：与 `agent.py` 一致，仍走
  `response_format={"type": "json_object"}`；真实运行里没有出现无法解析的 JSON。
- **C01 看不见中文数字**：Q2 的"七成""十四日""四成到六成"是通用知识，不来自工具，也拦不住（C01 只看阿拉伯数字）。
  这属于规则本体，本轮不改；是否要求通用知识类内容也带标注**待定**。
- **两个百分数相减的单位**：Q4 的"跑赢 16.74%"应为"个百分点"，`difference` 沿用了被减数的单位 `percent`。
  是否在两个 `percent` 相减时改用 `percentage points` **待定**。
- **聊天能否读卡的理由文字**：现在 `get_card` 不返回理由、止损依据、目标依据和失效条件，工具说明与提示词都要求
  模型说明"在详情页里"。让聊天直接引用这些文字（它们本身带事实占位符，可以原样放行）是更自然的做法，
  但它扩大了聊天读取的范围，**待定**。
- **余额是否长期显示**：接口已实现并测试，但本轮没有真实余额可看。
- **历史窗口是否够用**：12 条是当前取值，没有真实长对话可评估。
- **费用口径**：用高峰价作上界。若用户希望按实际时段估算，需要知道请求时刻，
  而"低峰价为高峰价一半"的时段规则（工作日 UTC 01:00–04:00 与 06:00–10:00 为高峰）
  已在 `pricing.json` 里注释，尚未实现按时刻选择。
